# 决策简报：情报站的排序轴选择与重构上线

> **这份文档是写给外部 AI 顾问的。** 我是项目所有者，**不是程序员**（AI 内容爱好者，平时用 AI 工具做产品和知识管理）。下面是自足背景 + 已查明事实 + 我卡住的决策，请重点回答最后一节的 4 个问题。
> 线上站点：https://bxs1024.github.io/weekly-report/ ｜ 生成时间：2026-10-07

---

## 结论速览

1. **项目**：一个自动运行的全球科技/互联网新闻情报站。每天采集 85 个信源 → 筛出合格事件 → 排序 → 生成静态页面。跑在 GitHub Actions + GitHub Pages 上，**月成本 $0**。
2. **正在做的事**：照开源项目 AIHOT 的方法论做重构，给每条事件加一套「AI 打分」，与原有的「程序打分」**并排跑**，未来可能用它替换排序主轴。
3. **核心矛盾**：两把尺子**只有 49.7% 意见一致**（197 条样本，相关系数 0.306）。这不是精度差异，是**取向差异**——程序分偏「资本动向」（融资/股价/财报），AI 分偏「行业变化」。
4. **一个关键澄清**：本站**分数只排序、不筛选**。显示什么由四道闸门决定，与分数无关。所以换排序轴**不会让内容消失，只会改变顺序**。（这点容易被误读，包括我自己一度也读错了。）
5. **我判断不了的**：哪把尺子更接近「读者想要的顺序」。这是价值判断，不是技术问题。
6. **另外三个已查明的问题**：① 采集任务近期 40 次运行有 25 次被取消；② 我本地副本停在 9-02，线上已到 10-06；③ 重构代码（41 个提交）还没上线，所以「并排跑两周」**一天都还没开始**。
7. **要你帮的**：最后一节 4 个问题。

## 一、项目是什么

**产品**：把散落在全球各地的英文科技/互联网新闻，整理成一份每天可读、可审计的中文情报简报。

**四层产品结构**：日报（今天先看什么）→ 周报（这周的方向和窗口）→ 月报（趋势与结构变化）→ 公司索引（单个观察对象的时间线）。

**规模**：

| 项 | 数量 |
|---|---|
| 注册信源 | 85 个（19 个在跑，9 个候选） |
| 重点观察对象（公司） | 52 家 |
| 事件库 | 3796 条 / 119 天（本地副本，2026-05-07 ~ 09-02） |
| 日均入库事件 | 约 32 条 |

**技术形态**：Python 采集 + Jinja2 渲染 + GitHub Actions 定时任务（北京时间 02:00 / 09:00）+ GitHub Pages 托管。AI 部分用 DeepSeek 主力、豆包降级。**全部在免费额度内。**

**我的约束**（重要，请把建议限制在这个框内）：
- 我不写代码，所有改动由 AI 工具代劳 → 方案要能被 AI 工具执行，不能依赖我手工维护
- 月成本必须保持 $0 或极低
- 项目已有自己的规范文档（`docs/ARCHITECTURE.md`），新做法要能写进规范

**已有的产品资产**（这次重构不动它们）：
- **四道闸门**：范围闸（是否在观察范围内）→ 相关度闸（是否与互联网/AI 相关）→ 价值闸（证据是否可信）→ 行动性闸（是否有商业动作）。这四道决定"什么够格展示"。
- **观察账本**：52 家重点公司的七种状态（活跃/安静/有变化未达门槛/采集失败…）
- **证据可追溯**：每条事件保留原始链接、信源层级、链接修复记录

## 二、这次重构在做什么

**对标对象**：开源项目 AIHOT（`github.com/KKKKhazix/AIHOT`）。它的价值不在代码，而在**方法论与工程规则**（提示词外置+版本化、AI 双评分+人工校准、事件归组、付费回执、页面不调模型等）。

**重构动机**（原有四个缺口）：
1. AI 提示词硬编码在代码里，改一次要动代码
2. 评分只有程序规则单一来源，没有 AI 评分、没有校准闭环
3. 去重只做"同一事件合并"，没有"后续进展归组"，也没有事件级热度
4. AI 调用没有回执（重试会重复付费）

**分 6 个阶段推进**（每阶段独立验证、独立提交、可随时停）：

| 阶段 | 内容 | 状态 |
|---|---|---|
| P0 | 架构契约文档 + 架构边界测试 | ✅ |
| P1 | 提示词外置到 `prompts/` + 内容哈希版本 | ✅ |
| P2 | AI 双评分 + 付费回执 | ✅ 代码完成，已落库 197 条 |
| P3 | 事件四关系归组 + 独立来源热度 | ✅ 代码完成，已接上首页/公司索引 |
| P4 | 巨石文件拆包（`fetch_news.py` 899 行等） | ✅ |
| P5 | 校准工具 + llms.txt / Agent 说明页 | ✅ 工具完成，待人工标注 |

**原计划的落地路径**：两套分数同时落库 → 并排观察 2 周 → 用数据验证 → AI 分主导排序、程序分退为兜底。

## 三、两把尺子的分歧（核心事实）

### 3.1 两把尺子分别是什么

- **程序分**（`signal_change_score`，0–100）：手写规则打分。按动作类型分档：政策 25 / 产品 24 / 融资 22 / 财报 18 / 扩张 18 / 招聘 12，再叠加公司权重、时间衰减等。**直觉上就是「有钱有量就给高分」。**
- **AI 分**（`ai_score_avg`，0–100）：把事件丢给大模型，问"这条值不值得读者知道"，**独立问两次取平均**（压掉单次评分的随机抖动）。

### 3.2 实测数据（窗口 2026-08-27 ~ 09-02，197 条事件）

| | 均值 | 中位 | 区间 | ≥60 分占比 |
|---|---|---|---|---|
| AI 分 | 50.0 | 51 | 0–78 | **35%** |
| 程序分 | 65.4 | 72 | 0–93 | **82%** |

- **门槛一致率 49.7%**（两边都 ≥60 或都 <60）
- **相关系数 0.306**（很弱——不只是松紧不同，排序本身也差很多）
- **AI 自身两轮分差**：均值 2.5、中位 0、最大 20、68% 完全相同 → **稳定性没问题，问题在取向**

> 注意：≥60 这条线只出现在对比报告里，用来数"两边同意几次"。**线上不按分数筛选**，所以 35% vs 82% 不代表"内容会少一半"。

### 3.3 具体分歧长什么样（真实案例）

**程序分高、AI 分低**（AI 不认为值得优先看）：

| 事件 | 程序分 | AI 分 |
|---|---|---|
| Canadian payment processor Helcim raises C$53m | 85 | 38 |
| Adyen stock holds above the EUR 1,070 mark | 81 | 48 |
| Rakuten Kobo's in-store e-reader expansion at Best Buy | 81 | 38 |
| Viral AI startup Instinct has raised $350M at $2.5B valuation | 80 | 48 |
| "Card fees have staying power"（一篇行业评论） | 70 | 33 |

**程序分低、AI 分高**（AI 认为值得一提，规则没识别）：

| 事件 | 程序分 | AI 分 |
|---|---|---|
| TRM Labs Taps MAS Veteran to Lead APAC Policy | 0 | 58 |
| Kakao Pay Insurance speeds overseas claim reviews with AI | 0 | 43 |
| Jumia Technologies (JMIA) Stock News Today | 0 | 28 |

**读出来的规律**：
- 程序分给"融资/股价/财报"高分，AI 给这类中不溜 → **程序分是「资本动向雷达」**
- AI 会给"人事任命、运营效率改进"等**非资本事件**分数，程序分给 0 → **AI 分更像「行业变化雷达」**
- 两者都不是"错"，是**在回答不同的问题**

### 3.4 我的倾向（供参考，不是定论）

我倾向 **C（混合）**：AI 分为主排序轴，程序分保留为兜底和权重项。理由是程序分对"例行股价波动"和"行业评论文章"给分过高，这类内容读者价值低；但纯 AI 分又会丢掉"融资规模"这种硬信息。不过我没有把握，想听你的判断。

## 四、另外三个已查明的问题

### 4.1 采集任务在掉链子

GitHub Actions 每天跑两次（北京 02:00 / 09:00）。**最近 40 次运行：25 次被取消、14 次成功、1 次失败。** 被取消的都是卡满 1 小时超时被杀（工作流设了 `timeout-minutes: 60`，且有 `concurrency: cancel-in-progress: true`）。

结果是数据有断档：9-26、9-28、9-30、10-04、10-05、10-07 都没有数据提交。约每天成功 1 次。

### 4.2 我本地副本是旧的（不是线上出问题）

我本地数据止于 2026-09-02，一度以为"数据停了 35 天"。查 GitHub API 后确认：**线上一直在正常更新，最新数据 2026-10-06**，只是我本地拉取被网络代理挡住了。**本文所有分析都是在旧副本上做的。**

### 4.3 重构代码还没上线

本地有 41 个未推送的提交（重构全过程）。按原方案"本地不推送"是有意的，但这意味着线上跑的是 33 天前的老版本，**"并排跑两周"实际一天都没开始计时**；且越拖，本地与线上分叉越远，合并越难。

## 五、需要你帮我判断的 4 个问题

### 问题 1（最重要）：排序主轴怎么选？

选项：**A. 继续用程序分**（不改，零风险）／ **B. 换成 AI 分**（"真的变了什么"优先）／ **C. 混合**（AI 为主、程序分兜底）。

我判断不了"哪把尺子更接近读者想要的顺序"。**有没有比"我看 20 条例子凭感觉判断"更可靠、更省力的办法？** 比如：有没有办法用现有数据构造一个客观的评判标准（不依赖我逐条人工标注）？

### 问题 2：人工标注 120 条值不值得做？

校准工具需要一批人工标好的"该展示/不该展示"样本（骨架已备好 120 条，其中 110 条可用），才能扫描出最佳门槛。但**线上不按分数筛选**，所以门槛本身暂时用不上。**在什么情况下这件事才真的值得做？我是不是可以先跳过？**

### 问题 3：采集任务怎么修？

超时被杀的根因可能是：单次采集任务太重（85 个信源 + AI 分析）、或 AI 调用太慢、或并发设置导致互相取消。**在不增加成本的前提下，优先查什么、怎么改？**（我不写代码，方案要能交给 AI 工具执行。）

### 问题 4：本地这份重构怎么处理？

41 个提交、基于 33 天前的代码，且本地方向和线上已经分叉（线上有 3 个我没有的数据提交）。**是应该尽快合并上线，还是先只推代码不启用新功能（用开关关着），还是别的做法？** 我担心"改了 33 天没上线"这件事本身会让后面的合并变得危险。

## 附：技术细节备查

- **分数只排序不过滤**：这是写进 `docs/ARCHITECTURE.md` 的不变规则。资格由四道闸门决定。
- **安全阀**：`AI_CALLS_ENABLED`（总闸）、`AI_SCORE_ENABLED`、`GROUP_ENABLED` 三个环境变量可单独关停新链路，关掉后行为与改动前完全一致。
- **成本模型**：每次 AI 评分约 2 次调用，日均 32 条事件估算 < ¥0.2/日；有付费回执，重试不重复付费。实测本轮全部改动累计花费 < ¥0.5。
- **事件热度两个坑（已修）**：① 本站去重层比归组层先跑，同一事件的多家报道入库时已被合并，所以"独立来源数"必须把被合并的兄弟报道算进来，否则恒为 1；② 热度的时间锚点必须取"数据最新日"而非机器时钟，否则数据停更后热度集体归零且不可复现。
