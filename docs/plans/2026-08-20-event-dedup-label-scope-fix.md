# 事件身份卡：AI 一次定案、下游只读的系统性修复方案

> 日期：2026-08-20
> 状态：方案 v2（第一性原理重想后的系统版，替代同日止血版）
> 关联：fdc1728（08-13 事件键去重已落地）、桌面文档（08-19 讨论的 B+C）

## 一、三个症状是同一个根因的三种投影

08-18/19/20 暴露的三个问题，表面互不相干：

| 症状 | 直接机制 |
|------|---------|
| Navi/Kakao Mobility/Kanana-2 重复漏并 | 去重靠正则从标题提取"主角"，措辞一变键就对不上；兜底 Jaccard 丢数字、不归一词形 |
| Kakao 被标「中资出海」 | 渲染层 `_is_chinese_capital`（generate_html.py:221）对全文做中资名单**子串匹配**，标题里的 "Alibaba"（被超越的对比对象）命中 → 覆写 AI 的正确标签 |
| 家得宝建材零售进入全部事件 | scope_gate 对 "L4 垂直精品源" 的**信源合约无条件信任**：Retail Dive 登记 track=电商，其所有报道（含传统零售财报）不再做内容相关性检查直接放行 |

回到第一性原理问：这三个环节（去重、打标签、定范围）到底在回答什么问题？**同一个问题——"这条事件到底是什么"：主角是谁、属于什么行业、主角是不是中资、事件是什么类型。** 系统里只有一处真正"理解"过每条事件——AI 分析那次调用。但现在的 AI prompt 只要了**叙事字段**（怎么复述、怎么点评），没要**结构字段**（主角是谁、涉及哪些实体及其角色、真实行业归属）。

于是每个下游消费者被迫各自用脆弱的启发式从标题重新猜：
- 去重猜主角 → 正则提取，措辞变了就错（Navi："Sachin Bansal's fintech Navi" vs "IPO-Bound Navi"）
- 标签猜中资 → 子串匹配，不懂语义角色（"Tops ... Alibaba Models" 里的 Alibaba 是对比对象不是主角）
- 范围猜行业 → 关键词 + 信源身份背书，信源说的不算数时报错（Retail Dive 自称电商垂直，实际是全零售媒体）

**三套启发式，三种不同的错法。补丁修一个，下一个批次换一个姿势再错（08-12→08-13 修过一轮，08-18/19 又冒出新姿势，已经证明）。**

## 二、系统方案：AI 产出"事件身份卡"，下游全部只读

### 原则 1：AI 理解，规则审计（决策权归 AI，关键词层退居审计员）

扩展 AI 分析 prompt，每条事件在原 7 字段之外多输出结构字段（**同一次调用，无额外 API 成本**）：

| 新字段 | 含义 | 谁消费 |
|--------|------|--------|
| `subject_entity` | 事件主角的规范名（"Navi"/"Kakao Mobility"），AI 直接认 | 去重键、聚合 |
| `mentioned_entities` | 其他被提及实体 + 角色（actor/competitor/mentioned/investor） | 中资判定、防误标 |
| `is_chinese_outbound` | 主角是中资公司且事件是其出海动作 → true | 中资标签页（替代渲染层子串匹配） |
| `industry_scope` | 内容真实归属的目标行业（scope_gate 行业表子集，可为空） | 范围闸门 |
| `amount_normalized` | {数值, 币种}，如 $100M → {100000000, USD} | 去重辅助、展示 |

关键词规则不删除，**降级为审计员**：AI 输出与规则交叉校验，矛盾即标记待审——
- AI 判 `is_chinese_outbound=true` 但主角不在中资名单 → 可疑，标记
- AI 判 `industry_scope` 为空但信源是 L4 合约源 → 可疑，标记（正是家得宝的形态）
- 同实体同类型同日两条但 AI 判不同事件 → 保留（防误并）

### 原则 2：一次写入，渲染只读

所有语义判定**只在入库时发生一次**，写入 events.json；`generate_html.py` 退化为纯读取。当前 705-710 行"渲染时覆写 insight_label"正是 Kakao 标签错误的反模式——数据层明明是对的（insight_label=背景补充、is_chinese_capital=null），展示层二次判定把对的改错了，且这种错在数据文件里查不到。修复：中资判定下沉为身份卡字段，渲染层只读。

### 原则 3：信源登记是"先验"，不是"通行证"

信源元数据（tier/track/scope_industries）回答的是"这个源声称报道什么"——只能影响**采不采、初筛松紧**，永远不能替代内容检查。改动：
- scope_gate 的 `source_confirmed` 通道增加数字产业相关性复验（DIGITAL_RELEVANCE_TERMS），合约源只降阈值、不豁免
- source_registry 审计修正：Retail Dive 的 track 改为「零售」（泛行业），不再挂 commerce 合约；其余 L4 源逐一核对"登记行业 vs 实际报道内容"

### 原则 4：质量门——回归集 + 周度审计（防第四类错误）

错误反复出现的原因：没有一个"已知坏模式清单"持续挡住回退。建立：
1. **黄金回归集**（进 run_tests，改代码即跑）：
   - 必须合并对：Navi×2、Kakao Mobility×2、Kanana-2×2、SEA×3、Jumia×2、Rakuten×2（08-12 批次）
   - 必须不合并对：Rakuten Bank vs Rakuten Securities、Kakao 财报日 vs 游戏新闻、财报方向相反对
   - 标签：Kakao/Alibaba 对比案例 ≠ 中资；蚂蚁国际外汇工具案 = 中资
   - 范围：家得宝财报必须被拦；真实电商融资必须放行
2. **周度数据审计脚本**（扩展已有 misclassification_audit / signal_funnel_report 基建）：扫近 7 天 events.json，查三类坏模式——合约放行但无数字相关性、疑似重复候选对、主角实体非互联网黑名单——产出报告进 run_metrics

## 三、去重如何被身份卡重构（回答 08-19 讨论的 B+C 方案）

桌面文档的 B+C 方案并入本框架，定位更清晰：

- **B（归一化增强）降级为兜底路径的改良**：老数据没有身份卡字段，仍走原逻辑——补数字归一（$100M/100 Mn→同 token）、词形归一（raises/raising→raise）、主语剥离修饰词（"IPO-Bound"类前缀）、IPO/上市申请补进融资锚点
- **新数据主路径**：去重键 = `subject_entity + event_types + 日期窗`，AI 定主角，正则主语提取逐步退役
- **C（AI 判重）保留**：键相同但类型不同、或键缺失的灰色候选对，批量丢给 AI 判"是否同一事件"——这是语义级兜底，解决 Kanana-2 双源深度改写这类任何词法都救不了的对
- 跨天合并天然受益：08-20 的 Navi 与 08-19 主角键一致，直接并入

## 四、分阶段实施

**阶段 0｜止血（半天，与本方案不冲突，先做）**
1. `_is_chinese_capital` 改实体级判定 + 对比语境排除（tops/beats/surpasses + 中资名 → 非中资）
2. Retail Dive 降级 + source_confirmed 通道加数字相关性复验
3. 展示层全部事件路径补 `is_mainline_internet_event` 兜底
4. funding 锚点补 IPO/上市申请
5. 存量清理：家得宝等越界事件、Kakao 标签修正

**阶段 1｜身份卡（核心）**
1. AI_SYSTEM_PROMPT 加 5 个结构字段 + 2 条审计规则交叉校验
2. fetch_news 入库时写入身份卡字段（analysis_status=complete 的事件）
3. 去重键、中资标签、scope gate 优先读身份卡，字段缺失回退旧逻辑（历史 3000+ 条不迁移）

**阶段 2｜渲染只读化**
1. generate_html.py 的 705-710 覆写逻辑移除，改读身份卡
2. 排查 generate_html.py 其余数据改写点（rewrite 类保留，语义判定类上移）

**阶段 3｜质量门**
1. 黄金回归集进 run_tests.py
2. 周度审计脚本 + 接入 signal_funnel 计数（每条被过滤事件都有可查原因）

每阶段独立可验证。阶段 0 当天见效；阶段 1-3 约 2-3 个工作日。

## 五、风险与不做的事

**风险**：
- AI 结构字段也可能错 → 审计规则交叉校验兜底 + 矛盾进待审队列，不静默放行
- 老数据无身份卡 → 回退路径保留（阶段 0 的归一化增强即回退路径的改良）
- prompt 加长后 AI 输出格式稳定性 → 沿用现有 JSON 解析与重试管线，加一条字段缺失的校验重试

**不做**：
- 不引入 embedding/向量库（08-13 附录 A 结论仍成立：日采几十条，身份卡 + AI 判重已是最优解）
- 不迁移历史 3000+ 条事件的字段（回退路径兼容）
- 不触碰 workflow 与数据 schema 结构本身（只加字段）
- 区域聚合（后置项）继续不碰；但身份卡的 `subject_entity` 未来可直接供公司变化聚合使用

## 六、验证标准

- 阶段 0：家得宝下线；Kakao Kanana-2 恢复正确标签；Kakao Mobility 双条合一
- 阶段 1：新批次事件 100% 带身份卡字段；黄金回归集全绿
- 阶段 3：连续一周审计无新增"合约放行无相关性""疑似重复对"告警
