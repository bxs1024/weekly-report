# 方案：从「稳定产出」到「可被验证的价值」——质量回路与能力收敛

> 2026-11-05 ｜ 状态：阶段 0 / 1 完成；阶段 2 已完成「归组 / 热度层拆除」（本地验证通过，发布待授权）；阶段 3 未授权 ｜ 适用范围：全球互联网动态情报站
> 本文自包含，假设读者没看过任何前期对话、代码或原始数据。

## 0. 结论块

1. **系统已经解决了「能不能稳定产出」，还没解决「产出的排序是否更接近真相」**；更关键的是，它现在连「自己有没有在靠近目标」都测不了。这是所有问题的共同根因。
2. **先建测量，再谈改动。** 28 天带双分的真实数据已够做离线回测，不需要等新的两周、不需要人工标注、不需要改线上。
3. **当前最缺的不是「选哪套分数」，而是「什么叫准」的定义。** 三套分相关性只有 0.19–0.30 只能证明它们不同，不能证明谁更准；此时把 AI 分切成主排序轴，是用一个未验证的判断替换另一个。
4. **「接上了但没产出」的能力不是待优化，是待验证有无存在必要。** 归组 6000 次 AI 调用只合并 28 次，而上更早的指纹去重已合并 186 条；先测「去重后还剩多少真重复」，再决定删、改还是留。
5. **死源和两个 workflow bug 是同一个病**：状态判断用了过期信息 / 失败被记录但无人消费。修法不是手工删 7 个源，而是建立「连续失败自动降级」和「基于最新状态」的机制。
6. **感知能力必须先恢复**：当前自检只回答「有没有生成」，不回答「生成的东西有没有用」；告警被 4 个月前的僵尸 Issue 压住。不修这个，任何改动都无法验证是否变好。
7. **方案阶段只出方案；后续代码改动需单独授权。** 阶段 2 的归组 / 热度层拆除已单独授权并在本地完成（见第 8 节）；涉及 workflow 的止血动作与对外发布仍未授权。

## 1. 背景

**产品是什么**：一个每天两次自动采集全球互联网 / AI 动态、生成静态页面的情报站。读者是需要在信息过载里判断「今天什么值得知道」的人（BD、投资、战略视角）。页面按事件发生日期组织，事件带程序分、AI 分、分层（A/B/C）、视图筛选、摘要、影响判断。

**一个月前做过什么**：P0–P5 架构重构。把长期撞 60 分钟超时被杀的单任务，拆成 `collect`（30 分钟，采集完先提交数据）→ `render`（90 分钟）→ `health-check` 三个任务；AIHOT 板块与主流程彻底隔离；双评分（程序分 + AI 分）、事件归组 / 热度、范围筛选等能力接进产线；补了更新日志的反向校验。

**当前状态（2026-11-05 线上快照）**：10-08 之后代码一行未变。主流程 55 次、AIHOT 58 次全部成功，单次采集均值 9.6 分钟；数据 183 天连续、6255 条；稳定期 28 天 1134 条，新字段覆盖率接近 100%；AIHOT 与源站实时比对 10/10 + 10/10 一致。

**体检发现的问题**（浓缩）：① 排序主轴仍是程序分，AI 分只落库；② 归组 / 热度空转（6000 次 AI 调用合并 28 次，`group_size` 全为 1，热度 92.5% 为 0）；③ 7 个信源 30/30 次全失败（3 个 RSS + 4 个 HTML）；④ CI 只跑 `--quick` 简版自检；⑤ collect 缺「同步最新 main」、僵尸告警 Issue #24 压住所有新告警；⑥ 模型榜官方明细是占位代码，9 家数据停在 2026-09-07。

**已有的决策前提**：`docs/2026-10-07-决策反馈.txt` 已就排序主轴选定 C 方案——「AI 主判断 + 规则做硬约束 / 兜底」，明确反对设死权重，并建议用历史数据做后视验证替代人工标注。该结论至今停留在纸面。

## 2. 要解决的问题

不是「修完上面 6 条」，而是：

> 这个系统缺少一条从「读者价值」倒推到「系统指标」的反馈回路。没有它，我们既不知道现在的排序好不好，也不知道每次改动是变好还是变差，更发现不了某个能力其实一直在空转。

因此本方案的目标有两个，且有严格先后：**（一）建立可观测的价值判据与回测能力；（二）只按回测结论裁剪 / 修改能力，并恢复系统感知自身失效的能力。**

---

## 3. 第一性原理推导

| # | 推导 | 直接后果 |
|---|---|---|
| 1 | 产品存在的唯一理由：帮读者在过载信息里判断「什么值得知道」。 | 唯一的质量函数是：**过一段时间回看，当时排在前面的内容是否真的更重要**。 |
| 2 | CI 成功率、字段覆盖率、AI 调用量、分数分布都只是投入 / 过程指标。 | 它们全绿不能推出「情报质量好」；「字段覆盖 100%」只说明写了，不说明有用。 |
| 3 | 三套分相关性 0.19–0.30 只证明它们在回答不同问题。 | 不能推出「AI 更准」。要选主轴，必须先定义「准」的可观测代理。 |
| 4 | 一个能力若长期零产出，说明它要解决的痛点可能不存在。 | 归组层要先验证「上游去重后是否还有真重复」，而非直接调判定阈值。 |
| 5 | 外部依赖（信源、源站页面结构）必然随时间变化。 | 健康度必须可衰减、可被看见，且判定口径写死在代码里；一次性删 7 个源解决不了下一次。 |
| 6 | 所有问题一个月无人察觉，是因为自检只查「有没有生成」、告警还坏了。 | **恢复感知能力优先于修具体功能**，否则改完仍无法判断是否变好。 |

**收敛判断**：先建测量 → 再裁剪 → 工程止血并行。任何不挂在「可观测判据」上的功能改动，都会重演「接上了但不知道有没有用」。

## 4. 方案：四个阶段

### 阶段 0 — 先定规则（约束先行）

在 `docs/ARCHITECTURE.md` 现有 26 条不变规则后新增 4 条，作为后续所有改动的约束：

1. **自动能力必须配有效性校验**：字段写进数据不算数，值必须有区分度；「全零 / 全同 / 命中率近零」要能触发告警。
2. **「准」必须先定义再优化**：任何排序 / 筛选改动，上线前必须有可观测的成功判据与回测结论，禁止直接调权重。
3. **外部依赖配健康度衰减**：信源连续 N 次失败自动降级、移出活跃列表，并在巡检输出里可见。
4. **自动提交与告警判据基于最新状态**：不得依赖任务启动时的仓库快照或「是否存在任意同名告警」。

验收：每条规则都有对应测试或检查函数；用反事实验证（把输入换回故障状态，确认检查真的会报）。

### 阶段 1 — 建立测量回路（决定一切优先级，零风险）

依赖：阶段 0。不改线上、不联网、不消耗 AI 调用、不动 workflow。

1. **先产出《重要性判据定义》一页**，把「更重要」翻译成可从现有数据算出的代理指标：
   - 新独立来源：T 日后 7 天内，同一主体 / 事件出现不同媒体（`publisher`）的新条目；
   - 后续进展：同一 `canonical_company` 或 `group_id` 在后续日期出现新动态；
   - 连续事件链：跨 ≥2 个日期形成链条；
   - 反例：三者皆无 = 孤立噪音。
   这一页需你确认后才跑回测——「什么算重要」是产品判断，不是技术判断。
2. **离线回测脚本**：读线上 `events.json`（走 git blob API，本地放 `.data/` 忽略目录），以稳定期 1134 条为候选、按 14 天完整回看窗口取实际可用的 568 条为样本，对比四种排序方案在「前 20 条 / 前 50 条里有多少后来被证实重要」上的表现：
   程序分 / AI 分 / 信号变化分 / 「AI 主判断 + 规则硬约束」（不设权重，用「AI 认为有变化 + 规则不否决重大事件」这类布尔组合）。
3. **产出一张对比表 + 一个明确结论**：谁是主排序轴、硬约束具体是哪几条、当前 C 方案是否成立。

验收：结论可复现（脚本 + 固定输入 + 固定输出）；样本量与局限写明；**不因为结果好看就改线上**。

### 阶段 2 — 按结论收敛能力（结果驱动，不预判）

依赖：阶段 1 的结论。

| 对象 | 先测什么 | 可能结论 |
|---|---|---|
| 归组 / 事件热度 | 上游指纹去重后，稳定期还剩多少真实重复报道（用标题相似度 + 主体 + 日期） | 若几乎无重复 → **删除该层**，省约 90% AI 调用；若有重复但 AI 判不出 → 换规则方案；若有效 → 修判定逻辑 |
| 死源 | 按写死的口径复算（连续 7 次失败且仍在活跃列表，仅 `failed` 算失败），再看这些源是否还有任何历史产出 | 建立「连续 7 次失败自动降级」，一次性清理存量；不手工维护黑名单 |
| 官方榜单明细 | 页面是否真的展示 `official_sources`、读者是否用得到 | 若未展示 → 删字段与抓取，不实现 turbo-stream 解析器；若展示 → 标出数据日期并实现 |

验收：每项都有「删除 / 保留 / 修改」的书面结论与依据；删除项同步清理测试与文档。

### 阶段 3 — 恢复系统感知（工程止血，可与阶段 1 并行，需授权）

1. `collect` 在 checkout 后补「同步最新 main」，推送被非快进拒绝时 rebase 重试 2–3 次（修 10-08 丢 17 条数据的根因）。
2. 告警判据改为「只认最近 7 天的告警」，关闭僵尸 Issue #24，替换已废弃的 `::set-output`。
3. CI 自检分层：每次运行的 `--quick` 增加 3 条**有效性断言**（字段全零、归组命中率、信源连续失败）；每周一次跑 full 模式的重复率 / 信源占比 / 订阅条数检查。
4. 对新增检查做反事实验证：人为关掉一个能力，CI 必须报警。

验收：模拟并发推送 collect 不再被拒；人为造一次失败，产生一条新告警；有效性断言在故障态确实触发。

## 5. 关键决策与被放弃的备选

| 决策 | 理由 | 放弃的备选及原因 |
|---|---|---|
| 先定义「准」，再改排序轴 | 没有判据就无法区分「变好」和「变了」 | 直接设 AI 70% + 程序 30%：把拍脑袋选 A/B 变成拍脑袋选比例，决策反馈已明确反对 |
| 用历史数据离线回测 | 183 天数据、稳定期双分齐全，成本近零、当天可出结论 | 人工标注 120 条：成本高、滞后，且分数只排序不筛选，找门槛不是当前核心 |
| 并排观察改为「回看历史」 | 10-07 反馈指出「两周」应理解为 10–14 个完整成功数据日；现在已有 28 天 | 再等两周并排观察：只新增数据，不新增判断力 |
| 归组先测必要性再决定存废 | 上游已去重 186 条，痛点可能不存在 | 直接调 AI 判定阈值 / 换模型：可能是在给不需要的能力加成本 |
| 死源建机制而非删清单 | 外部依赖必然持续变化 | 手工删 7 个源：下次源改版照样静默失败 |
| 感知能力优先恢复 | 否则无法验证任何改动是否变好 | 先修读者体验（配图 / 页面体积 / 跳转链接）：是舒适度问题，不是价值问题 |
| 四维度情报价值模型延后 | 它是长期方向，但依赖「准」的定义 | 现在实现：会用另一套未验证的维度替换未验证的分数 |

## 6. 明确不做

- 不设死权重、不把 AI 分直接切成主排序轴、不做人工标注校准集、不实现四维度情报价值模型。
- 不重写页面、不拆 `index.html`、不做前端优化（4.49 MB 排到最后）。
- 不同时修全部 6 类问题，避免又一轮「改完不知道有没有变好」。
- 不改 workflow、不接 CI、不改产品代码、不推送；阶段 0 只允许落规则文档与 `scripts/test_*.py` 形式的可执行规格。

## 7. 已知限制与风险

- **样本窗口**：AI 分在稳定期覆盖 100%，但全历史仅 21.4%，回测只能用 2026-10-09 起的 1134 条；按用户确认的 14 天完整回看窗口，实际样本缩到 10-09~10-22 共 568 条；**T+30 尚未到期**，结论需注明是短期代理且统计厚度有限（前 20 只差 3 条）。
- **代理指标不是真理**：「新独立来源 / 后续进展 / 事件链」只是重要性的近似，不能替代真人判断；它决定的是「哪套分更会预测后续」，不是「哪套分更懂业务」。
- **信源口径必须写死，且要覆盖全部分区**：体检的「7 个 30/30 全失败」= 3 个 RSS 源 + 4 个 HTML 源。阶段 0 实现检查时踩过两次坑：只聚合 `rss.source_stats` 会漏掉全部 HTML 源（误以为只有 3 个）；把 `status='empty'`（页面正常但当天无新稿）也算失败会多报 26 个。两者都是规则 1 要防的「检查接上了但没接全」。现由 `build_source_state()` 固定口径（合并 rss/html/company，仅 `failed` 算失败）；按「连续 7 次失败」实报 8 个，比人工清单多抓到一个新近变坏的 RSS 源——机制比清单更有用。
- **无读者行为数据**：站点没有点击、停留、收藏埋点，无法测真实阅读价值；如需，须另立需求。
- **数据口径**：`group_id` 全为 `single`、热度近全零，回测不能依赖这两个字段做标签。
- **外部依赖**：AIHOT 源站已有反爬（不带浏览器 UA 返回 403），抓取随时可能再次失效；现有空结果非零退出 + 保留旧数据可防数据被清空，但需有效性检查才能发现「长期沿用旧值」。
- **公开性**：`docs/` 是 GitHub Pages 根目录，本文会随站点公开可访问（与既有计划文档同等待遇）。
