# 数据保全与渲染解耦（2026-10-07 定稿）

> 前序：`docs/plans/2026-10-06-aihot-methodology-refactor.md`（P0–P5 方法论重构，已落地）
> 本文档只处理本轮新查出的**生产可用性问题**：采集数据持续断档。

## 结论速览

1. **数据断档的真凶不是 AI 慢、也不是运行之间相互取消**——25 次 cancelled 全部卡满 60.3 分钟（job 上限），是**超时**。
2. **渲染占 33–57 分钟**（HTML 17–33 + RSS 16–24），采集+AI 只占 5–9.5 分钟。瓶颈在渲染。
3. **最要命的是提交排在渲染之后**：`git add data/ docs/` 在最后一步，渲染一超时整 job 被杀，提交 skipped，**当天数据全丢**。
4. 渲染慢的实测根因有两个：**整站装配被跑了两遍**（HTML 一次、RSS 又一次），且装配里**展示层判重是 O(n²)**（2062 条输入约 186 万次判定）。
5. 编辑层缓存**输入指纹随数据漂移**，导致每次渲染都为历史周/月重发付费请求（本地实测一次渲染 7 次调用、占渲染总耗时约 2/3）。
6. 已执行：拆 job + 数据检查点 + 封档周期只读缓存 + 判重按日期分桶 + RSS 复用装配。**全量离线套件 35 PASS / 0 FAIL / 3 SKIP。**
7. **已上线（2026-10-08，`5bba1e8` 起随 `52e1cc9` 合并推送）**：新流水线首次实战 23 分钟 success（旧版长期贴着 60 分钟超时），`Generate HTML` **28 秒**（旧 17–33 分钟）、`Generate RSS` **0 秒**（旧 16–24 分钟）。

## 已执行改动

### ① 数据保全（P0，已改）
`.github/workflows/update.yml` 拆成两个 job：

- **`collect`（30 分钟上限）**：离线测试门控 → 采集 → 修复历史问题事件 → **数据检查点**（`git add data/` 单独提交推送）
- **`render`（90 分钟上限）**：同步最新 main → Generate HTML → Generate RSS → Verify output → 提交页面（`git add docs/ data/`）

关键点：job 级 `timeout-minutes` 到点杀进程，但**已完成的步骤仍然生效**——提交只要排在渲染之前，渲染超时就只丢页面、不丢数据。

`health-check` 改为 `needs: render`；`notify-failure` 改为 `needs: [collect, render, health-check]`。

### ② 渲染解耦与提速（P1，已改）
- **封档周期只读缓存**：`reports/period.py` 传 `allow_ai = status != 'closed'`；`editorial.py` 新增 `allow_ai` 参数，封档周期只用缓存（旧版也接受），**完全没缓存才退回一次 AI**（避免整页生成失败）。AI 调用从每次 7 次压到最多 2 次（当前周 + 当前月）。
- **RSS 复用装配**：`generate_html.py` 把 RSS 需要的字段落到 `data/.cache/rss_context.json` 并附 `events.json` 指纹；`generate_feed.py` 指纹相符就复用，否则重算。指纹机制保证不会用到过期上下文。
- **判重按日期分桶**：`dedupe_display_events` 按「日期 ±7 天」分桶，并显式补上三条**不看日期**的判同路径（URL 相等、`_fingerprint_match`、空日期）。候选按 kept 下标升序回放，结果与全量扫描逐条一致。
- **计时插桩**：渲染步骤加 `PYTHONUNBUFFERED=1` 与 `⏱ …用时 N 秒` 输出——原日志全挤在最后一秒，无法定位热点。

### ③ 附带修掉的一个隐患
`editorial.py` 原先把「没有 AI 通道就返回 None」放在**缓存查询之前**，导致 `AI_CALLS_ENABLED=0` 时连已缓存的周期也一并失败、整页生成抛「拒绝发布降级版」。现在缓存优先。
